01项目背景与痛点

WHY

年轻人的钱不是「记不清」，而是「看不见问题」。微信、支付宝、银行卡、信用卡的账单散落在多个入口；自动续费在几十块钱的量级上悄悄扣款；深夜冲动消费事后无感。传统记账工具回答了「钱花在哪」，却没有回答「账单有什么问题、下一步怎么办」。

痛点四类高频消费困境

痛点典型场景SpendCT 的回答
账单零散微信 / 支付宝 / 银行卡多入口，月末对账靠翻聊天记录多格式账单一键导入，浏览器内解析合并去重
订阅陷阱自动续费低额高频，注销入口隐蔽，用户到退款时才察觉确定性规则扫描连续扣费，附下次扣费倒计时与取消指引
冲动消费深夜下单、直播抢购，事后复盘无抓手异常检测阶段标记深夜 / 大额 / 高频异常，量化损失
预算失守记账 App「记录有余、诊断不足」，预算形同虚设12 类目预算环 + 超支贴士 + 下月预测 + 一句话记账

定位目标用户与产品主张

目标用户：大学生与年轻上班族——消费场景丰富、财务经验不足、对隐私敏感、习惯「先看结论」。

定位一句话：不是又一个记账工具，而是「体检 + 处方」——像体检报告一样，先出结论与证据，再给可执行的改善动作。
  • 结果先于对话：AI 先把体检结论写成带证据的洞察卡流（可审阅、可存档），用户带着具体问题点卡片追问，而不是从空白聊天窗开始；
  • 结论可溯源：每张洞察卡带置信度、图表证据与引用（聚合 SQL / 订阅规则 / 案例库 / 工具），低置信度结论自动挂起（宁缺毋滥）；
  • 隐私可见：账单明细只在浏览器内计算，服务端只转发脱敏聚合摘要，数据可见性对照表公开在产品内。

02产品概述与核心功能

WHAT

SpendCT 把微信、支付宝导出的账单 CSV 拖进浏览器，一条六阶段流水线自动完成清洗 → 消费画像 → 异常检测 → 订阅陷阱扫描 → 环比归因 → 年度报告，产出可确认、可质疑、可深挖的消费洞察卡。全过程实时可见、可暂停、可断点续跑。

05隐私与数据安全（亮点）

PRIVACY BY ARCHITECTURE

传统账单工具需要把账单上传云端才能做分析。SpendCT 的隐私不是「承诺不偷看」，而是架构上就没有上传通道：解析、聚合、体检全部发生在浏览器内的 DuckDB-WASM 列式引擎里。

对照表每一步的数据可见性

环节数据形态去向
账单导入原始 CSV（含交易明细）仅浏览器内存，不落盘、不上传
六阶段聚合SQL 分组聚合结果（9 预计算表 / 13 视图）浏览器内
LLM 叙事 / 建议聚合统计值（金额分箱脱敏 + 数据集哈希）服务端转发，不存任何请求日志
字段映射 AI 兜底表头 + 至多 1 条样本行（≤6KB 截断）仅在探测链全失败且用户确认后发送
账户凭据PBKDF2-SHA256 加盐哈希（15 万次迭代）IndexedDB 本地
断点 / 缓存键阶段进度 + 数据集哈希localStorage 仅存键（红线：不落任何行数据与聚合明细）

红线三条不可逾越的约束（07 权威契约 §17）

  • localStorage 红线：不存任何行数据与聚合明细，只存哈希与进度键——刷新后数据随内存库消失，由断点条引导重新体检；
  • 密钥红线：API 密钥只走环境变量（.env.example 提供模板），`NEXT_PUBLIC_` 前缀禁用，pre-commit 的 check-secrets 钩子扫描历史防泄漏；
  • 数据主权：账单 CSV / JSON 一键导出、一键删除；删除后 IndexedDB 不留痕；数据可见性对照表直接公开在 /privacy 页面。

账户本地账户模式

账户体系完全本地化：注册 / 登录 / 会话全部在 IndexedDB 完成（PBKDF2-SHA256 加盐哈希），演示账户 demo / demo123 即开即用；个人中心提供成就段位、数据导出与删除入口。选择本地账户而非云端账户，是「账单数据不出浏览器」承诺的自然延伸——没有账户服务器，就不存在账户数据泄露面。

协议状态机与事件流（spendct协议@2）

管线是一台严格的状态机：每阶段 pending → running → succeeded / skipped / failed，阶段失败发 error 事件并降级继续（不中断整次体检）；运行可暂停（中止保留已产出卡）与断点续跑（从最近断点阶段重跑，阶段结果确定性保证产出一致）。

事件组事件（共 20 类）
运行边界（4）run:start · run:complete · abort · checkpoint:saved
阶段（5）stage:start · stage:thinking · stage:evidence · stage:complete · stage:skipped
洞察卡（3）card:delta · card:complete · card:withheld
LLM（2）llm:degraded · llm:repair
RAG / 工具 / 反思 / 缓存（6）rag:retrieved · tool:start · tool:end · reflect:result · cache:hit · error（8 错误码判别联合）

闸门SQL 白名单与发布闸门

  • 确定性主体：体检结论全部来自代码常量的白名单 SQL（9 预计算表 + 13 视图），LLM 只负责叙事与建议——结论可复现、可审计；
  • SQL 白名单：追问场景 LLM 生成的 SQL 必须通过窄文法预检（7 原因码逐条解释拒绝理由），执行层行数复检 + 3s 超时中断，只读连接无写权限；
  • 发布闸门（reflect）：每张卡自检 confidence ≥ 0.6、阶段证据 ≥ 2 行、统计值非全零，全部通过才 published，否则 withheld 并明示原因——宁缺毋滥，低置信度结论不抢高位视线。

07智能能力：LLM 与 RAG

THE BRAIN

智能层遵循一条原则：模型只做「锦上添花」，不做「一锤定音」。体检结论由确定性 SQL 给出，LLM 负责把聚合数字写成有洞察的叙事、生成可执行的建议、回答锚点追问——任何模型失败都不影响体检结果本身。

  • mock / live 双模式：三个密钥全空时服务端强制 mock 模式——演示、测试、断网全链路可用；配置密钥后切 live；
  • 指数退避：上游限流时按退避策略切换，过程通过 llm:degraded 事件在思考面板如实展示（不伪造进度）；

12结语

消费CT 想做的，是让每一个年轻人的账单都值得被认真对待——体检出问题，处方给动作，数据留本地。

从「账单零散」到「体检 + 处方」，从「云上分析」到「明细不出浏览器」，从「空白聊天窗」到「可审阅的洞察卡流」——SpendCT 在交互范式与隐私模型两个维度上给出了自己的答案。项目的每一行代码、每一条契约、每一个测试，都记录在公开仓库的提交历史与开发日志里。

感谢评委的时间与关注。
